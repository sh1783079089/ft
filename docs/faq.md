# 常见问题与开发记录

## 1. 编译问题

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| `'gcc' 不是内部或外部命令` | MinGW-w64 未安装或 PATH 未配置 | 安装 MinGW-w64 并确认 `bin\` 在 PATH 中；或用 CLion 打开项目（CLion 自带 MinGW） |
| `CMake Error: Could not find CMAKE_C_COMPILER` | CMake 找不到 gcc | 先解决 gcc 的 PATH 问题；或直接用 gcc 一行命令（见 `building.md` 方法一） |
| `fatal error: conio.h: No such file or directory` | 在非 Windows 系统上编译 | **本项目仅支持 Windows**。切换到 Windows 编译；或在 Linux 上使用 MinGW 交叉编译（`x86_64-w64-mingw32-gcc`） |
| `fatal error: direct.h: No such file or directory` | 同上 | 同上 |
| CMake 报 `Could not find Ninja` | 未安装 Ninja | 用 `-G "MinGW Makefiles"` 指定 MinGW Make 生成器（见 `building.md` 方法二） |
| `undefined reference to '__imp_xxx'` | 链接时缺少 Windows 库 | 使用 gcc 编译一般会自动链接所需库；若出现此错误，加上 `-lkernel32 -luser32` 等参数（通常不需要） |

## 2. 运行问题

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| 双击 `file_tracker.exe` 闪退 | 这是控制台程序 | 在终端中运行：`.\file_tracker.exe` |
| 终端中文乱码 | 编码不是 UTF-8 | 先执行 `chcp 65001`，或使用 **Windows Terminal** |
| 输入文件路径后提示“文件不存在” | 路径输入错误或文件未创建 | 用记事本创建目标文件；使用**绝对路径**，如 `C:\test\hello.txt` |
| 输入路径后提示“无法创建仓库目录” | 目标目录无写入权限 | 换一个有写权限的目录 |
| 路径中包含中文时异常 | 程序用 ANSI 方式处理路径 | 确保终端编码为 UTF-8（`chcp 65001`），路径不含特殊控制字符 |
| 程序执行到一半闪退/崩溃 | 输入了非法字符 | 按提示重新输入；若严重崩溃可重新运行，`.ft\` 数据目录不会损坏 |
| 监控模式无法检测到文件变化 | 文件修改后保存时间太短 | 监控轮询间隔为 5 秒；若用脚本瞬间修改文件可能被跳过，请正常用编辑器保存 |

## 3. 功能问题

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| 连续两次提交同一内容，版本描述重复 | 内容未变化，程序不应生成新版本 | 检查是否真的修改了文件内容再提交；SHA-256 去重逻辑应该会拦截重复 blob |
| “已在其他分支检出”提示 | 当前 `checked_out` 指向的版本不是当前分支的 head | 提交一次新版本即可“跟上” |
| 提交图看起来简单，看不出分叉 | 分支是在第一个版本就创建的 | 先提交几个版本到 `main`，再创建分支切换过去提交，分支点会更明显 |
| 标签删不掉 | 标签名区分大小写 | 输入标签名时注意大小写，确保与创建时完全一致 |

## 4. 开发过程记录

开发过程中通过人工测试和代码审查定位并修复了多个真实缺陷，代表性案例如下。

1. **含空格路径读取截断**。最初使用 `scanf("%s")` 读取文件路径，遇到空格即截断，含空格的绝对路径解析必然失败。改为 `fgets` 整行读取并去除行尾换行，同时增加读取失败的 NULL 检查与 EOF 保护，避免输入流异常时死循环。
2. **SHA-256 轮常数录入错误**。早期版本个别轮常数 K 抄录有误，摘要与标准结果不一致。通过对同一文件用系统工具独立计算摘要并逐一比对定位，修正后所有测试文件的哈希与独立计算结果完全一致。
3. **路径缓冲区截断隐患**。仓库内部路径由“工作目录 + `.ft/repos/<文件名>` + 元数据名”拼接而成，可能超过 `MAX_PATH_LEN(260)`。将相关缓冲区扩容为 `REPO_PATH_LEN(324)` 与 `STORAGE_PATH_LEN(452)`，拼接统一改用 `snprintf` 并检查返回值，超长时拒绝操作并提示用户缩短路径。
4. **元数据解析防御不足**。`split_line` 早期允许字段数少于期望值，损坏行可能以残缺数据进入链表；现要求字段数与格式精确匹配，不合法的行整行丢弃。`storage_load_commits` 增加 ID 越界检查并对映射数组显式零初始化。排查中还发现 `.ft/index` 去重逻辑因按单字段解析而永久失效，改为按“文件名\|全路径”双字段解析后修复。
5. **分隔符注入**。提交说明、分支名、标签名若包含元数据分隔符 `|`，会破坏按行存储格式并在下次加载时污染数据。新增 `storage_text_is_safe`，在录入环节直接拒绝包含 `|` 的输入。

### 已知不足

- 元数据保存尚未采用原子写入、文件锁和崩溃恢复日志，多进程或意外中断时仍有一致性风险。
- 提交入口未拦截超过 `MAX_COMMITS` 的新提交，超限记录在下次加载时会被跳过。
- Windows API 与 `system` 命令限制了跨平台能力。

后续可增加提交删除与引用回收、原子写入、文件锁、哈希流式计算和单元测试，并把平台相关监控与终端操作封装为适配层。
